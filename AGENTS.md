# Workflow delivery and execution efficiency

- Follow the active queue in `docs/PLAN.md`. Historical task numbers, role
  documents and residual specifications do not override it. Keep one coherent
  implementation increment active and detail only its next ready successor.
  Respect the user's current pause/resume instructions; a planning update does
  not resume implementation or authorize agents.
- At task entry, freeze a concrete user-visible exit, unresolved requirement/
  command IDs, consumed settings, actual API signatures, owned files and affected
  checks in the existing task record. Inspect a maintained real caller/control/
  output route before editing or launching broad verification.
- Prefer complete usable workflows built on accepted primitives. Do not make
  every point-tool, analysis, format or platform variant a prerequisite for an
  independent editing/viewing workflow. Keep unfinished variants explicitly
  assigned to their existing owners; advancing another task does not close them.
- Expand the current increment only for a concrete failing consumer, required
  behavior or demonstrated correctness/resource dependency. Record that reason
  in its existing task record. Defer unrelated optimizations and speculative
  infrastructure to an owning task; do not add generic schedulers, registries,
  harnesses or audit frameworks without a demonstrated need.
- Before expensive compilation, inspect all affected callers, binding mutability,
  exception types, synchronous/asynchronous timing and probe event/receipt schemas.
  Batch related core/header/binding/UI edits, use useful narrow checks first,
  then perform one coherent build per affected platform in its active cache.
  Preserve line endings; compare proposed bytes with existing bytes before
  writing, and skip byte-identical writes that invalidate build timestamps.
- Choose verification from changed behavior and dependencies. Reuse matching
  evidence for unchanged inputs; a corrected test, probe or receipt does not
  justify restarting an unchanged campaign. Shared ownership/numerical/public
  contract changes still require their affected regression, lifecycle and
  installed-client checks. Broaden when failures or release gates warrant it.
  Before installed checks, identify each changed module's install component and
  verify its loaded path and bytes against the built artifact, including optional
  extensions and changed pure-Python exports. Compare pure sources with installed
  bytes as well as checking loaded origins. The `Unspecified` component does not
  include every Python module or install the pure package; use `processing-python`
  for its exports when appropriate.
- Missing references or an unrelated platform gate block only the claims that
  depend on them. Record exact missing inputs and advance independent work;
  repeat recovery searches only when a new plausible source exists. Preserve
  numerical correctness, commercial eligibility, data/history and applicable
  cancellation/resource guarantees. Final supported-platform release gates remain.
- Report scoped delivered behavior and remaining gaps at closeout. Reconcile
  stale progress links in place; do not equate family breadth, task counts or
  test totals with overall completion. Record available build/check time, retries
  and generated bytes in the existing receipt, without adding telemetry or a
  second progress ledger. Evaluate process improvements from subsequent results,
  not from publishing another plan.

# Required execution checkpoints

These checkpoints apply to every task, including fixes and documentation. Use
its existing task record; do not create another checklist, ledger or runner.
They are execution requirements, not suggestions. Complete the applicable
checkpoint before its dependent action; mentioning the rule or promising later
compliance does not satisfy it.

- At task entry and after a handoff or context compaction, read these instructions
  and the current task record. Reconcile live processes, receipts and outstanding
  cleanup before resuming. Reuse completed work; do not restart verification
  merely because conversational context was lost.
- If a checkpoint is unsatisfied, stop only its dependent action, record the
  missing evidence or concrete blocker, and correct it within existing authority.
  Continue independent safe work. Do not waive a checkpoint because a prior task
  skipped it, because the user says continue, or because a deadline is near.
  Apply explicit user overrides within their stated scope.
- Before each dependent action, record the applicable checkpoint evidence in the
  existing task record or its referenced receipt: observed result, exact paths,
  unresolved unknowns and the decision to proceed or stop. Do not backfill a
  preflight after launching the action, treat a plan as evidence, or infer that
  a checkpoint passed because a previous agent or summary said it did.
  Recheck evidence when its consumed inputs, process state or storage change;
  reuse still-valid evidence instead of repeating scans or green campaigns.

- Before a build, install or verification run, inspect live processes and existing
  receipts. State the changed input or unresolved risk requiring that run, its
  affected targets, and the existing cache/runtime/scratch paths. Resume or collect
  an active run instead of launching a duplicate. A tool timeout is not proof
  that its process exited. Use the maintained process-ownership helper for
  long-running commands and collect its exit/cleanup receipt before retirement.
  Check the resolved cache/runtime paths against their recorded identities;
  change retry receipt names explicitly, never by global substitution across
  commands containing cache identities.
- Before selecting reference-dependent checks, verify that their required inputs
  exist at the consumed paths, including environment-selected reports and their
  producer/reader mapping. Record unavailable checks separately from passing
  checks; do not recreate retired build trees, change historical expectations or
  repeatedly launch a suite whose required reference is known to be unavailable.
- Before substantial verification, record the complete normalized storage scope,
  inaccessible roots and physical free space. If budget compliance is unknown,
  report it as unverified and bound the planned allocation explicitly; do not
  treat unknown bytes as available capacity. Resolve a known budget/disk-space
  problem before starting work that would worsen it. If generated bytes exceed
  the recorded allocation, stop further storage-growing verification, measure
  the actual scope and retire terminal scratch safely. Record the overrun and
  a measured revised allocation before resuming; do not silently increase the
  old estimate or relabel unknown storage as budget compliance.
- Before deletion, verify the absolute owned target, active-process use and link
  boundaries. Preserve required diagnostics and verify retained hashes first.
  If those checks fail, leave that target intact and record the concrete blocker;
  continue independent safe work. Never delete active scratch to satisfy cleanup.
- Before closing a task or starting its successor, finish safe retirement of its
  terminal disposable scratch and record retained evidence, cleanup results and
  unresolved blockers. For substantial verification, include before/after storage
  measurements. A promised later cleanup does not satisfy this checkpoint.
  Cite actual receipt paths and observed outcomes, including failures and unknown
  storage. An unresolved safety blocker must name the retained target and reason;
  it is not evidence of successful cleanup. Carry it forward explicitly before
  independent work proceeds.
- When a checkpoint is missed, record the actual lapse and corrective action in
  the same task record. Do not claim compliance from updating these instructions,
  or repeat unchanged builds merely to produce a cleaner receipt. For a repeated
  lapse, put the concrete corrective check immediately before the next affected
  action and record its observed result. Another policy edit alone is not the
  corrective check. Final reports must distinguish rules added from compliance
  actually verified; instruction text is not an automatic filesystem guard.

# Local build and verification storage

- Keep one active compiler cache and one active installed verification runtime per platform.
  Reuse the active cache; do not create a build/environment generation for each
  feature packet, retry or observation run.
- Preserve active compiler intermediates during routine cleanup when the storage
  budget allows. Reclaim them for necessary disk pressure or an explicit cleanup
  request, recording that future verification will recompile them.
- The historical project `build/` generations were retired at the user's
  request. Do not recreate them. Local Windows verification uses
  `.cache/native-verification/`; reuse the configured Linux cache when available.
  Disposable CI runners may use their workflow's paths.
- Use fresh, explicitly owned test scratch. After the process exits, retain
  small result receipts and losslessly compressed necessary captures, verify
  their hashes, then remove the scratch. Preserve failure diagnostics before
  deleting failed-run scratch as well.
  Linux filesystem/publication checks use host-local Linux scratch, not `/mnt/c`
  or another 9P mount. Own WSL descendants through the existing nested Linux
  process helper; hash-verify any necessary evidence transport before retirement.
- Do not archive whole compiler caches, virtual environments, dependency SDKs
  or repeated source checkouts as evidence. Record their identities and hashes.
- Measure generated storage before and after substantial verification. Normal
  focused work should stay within an 8 GiB working budget across active caches,
  scratch and retained local evidence. If a necessary check needs more, document why and clean its
  temporary data immediately afterward.
- Check physical free disk space before long builds and at their existing
  checkpoints as well as measuring project-owned storage. Unknown subtree sizes
  and logical budget headroom do not establish physical free space.
- Inventory the complete project `.cache/` and `.tmp/` roots, public retained
  review artifacts, and the existing Linux/dependency/runtime roots. Counting
  only `.cache/native-verification/` omits obsolete uv wheel generations.
  Normalize overlapping roots and count them once. An inaccessible subtree is
  unknown, never zero; report the budget as unverified until it can be measured.
  Preserve historical measurements and add a scope correction rather than
  relabeling their old root sets as complete.
- Before large UI verification groups, estimate producer/private, transported
  reader and Python capture copies against measured storage. Retain and retire
  terminal groups serially when accumulation could exceed the normal budget;
  do not wait for a full campaign closeout. Unknown subtrees are not headroom.
- Keep local capture retention bounded. Retain concise receipts and hashes
  before retiring superseded bulky captures; record their retirement explicitly.
  Prefer CI artifact retention for historical full capture sets.
- Verify absolute deletion targets remain inside the intended owned directory.
  Never follow junctions or symlinks during cleanup. Preserve source changes and
  leave other projects and unrelated global caches untouched.
- Keep historical expectations and fingerprints unchanged. A retired artifact
  is unavailable evidence; report that limitation instead of repinning it or
  claiming the full ImageJ/Fiji goal is complete from focused checks.

## Task closeout and waste management

- Use `docs/PLAN.md` as the current queue and completion policy. The historical
  ledgers preserve prior scope/evidence. Archived commands are evidence, not the
  current execution queue. Do not append milestone histories to the
  three live execution guides.
- After every task, perform the brief waste review in
  `docs/PLAN.md#task-closeout-and-waste-review`, including documentation/fix tasks.
  Record delivered scope, relevant checks, cleanup and a fix/defer/no-action
  decision. Assign material deferred waste to an owning task and update the
  current queue when the evidence changes priority or dependencies.
- Review unnecessary copies/scans, duplicated logic/guards, new controllers,
  shared-header/build fanout, redundant verification, one-off runners, repeated
  documentation and retained generated data. Distinguish measured effects from
  hypotheses. Do not turn each closeout into a full audit or speculative rewrite.
- Prefer existing checked-in CI/ownership/retention tools and parameter data to
  a new temporary executable runner. Preserve referenced historical identities
  before retiring superseded tools or artifacts; do not edit old expectations.
- Select checks by changed behavior/dependencies. Reuse green results for
  unchanged consumed inputs; broaden for shared changes, failures or release
  gates. Documentation-only tasks require document checks, not product builds.
  Confirm affected API declarations, return timing, binding mutability and
  exception types before writing their assertions. Review changed allocation/ownership paths
  before installed-client verification; keep owned consumer scratch until that
  review and final checks finish, then retire it. Premature retirement causes
  avoidable reconfiguration when review finds a fix.
- Report implemented, verified (with scope), integrated and release-ready aspects
  separately. A full-family certification counter is not the daily progress
  measure. Preserve strict licensing, numerical, data/history and applicable
  resource/cancellation guarantees.
