## One outcome and its boundary

Add **Composite Max** to the existing native channel-display pipeline, installed
C++/Python interfaces and shared ImGui panel. In Composite mode, map each visible
channel through its existing processor-specific range and LUT, then take the
maximum red, green and blue component independently. Reuse ordinary XY and
linked XY/XZ/YZ rendering, retained per-C sources, threshold/annotation boundary,
limits and source-bound display publication. The result must be distinguishable
from SUM using overlapping color components; ordinary disjoint RGB palettes
alone are an insufficient test.

This is not Max intensity projection along Z. It changes no dataset axes,
pixel values, geometry, channel order or stored ROI records. Min rendering is
now an explicit consumed dependency of the Max transition. Standalone Min/Invert controls,
the standalone Invert LUTs command, GUI Auto-contrast, LUT editor/interchange,
split/merge and Arrange Channels remain their existing follow-ons. A small
all-channel LUT transformation needed specifically by a Max-entry transition
may be a consumed contract; it is not acceptance of the standalone inversion
workflow. Adoption002 explicitly admits resolved Min; it grants no standalone
Min/Invert workflow acceptance.

## V01: compatible state and action representation

**Adopted option: an explicit exact stateV2 and actionV2, with adoption002's Min delta.** Keep the same
`channel_display` property and schema names, with integer version dispatch.
StateV2 adds a required `projection` enum `sum|max|min` alongside the existing exact
`mode` and `channels`; projection is retained while mode is Color/Grayscale but
affects rendering only in Composite. All channel/LUT/range/type/count rules
remain strict. StateV1 stays exactly `{schema,version,mode,channels}` and means
SUM; it must still reject a `projection` field, unknown enums and Boolean/float
versions. No implicit migration or rewrite during render, navigation, readback
or generic Save/Open.

Illustrative admitted V2 state shape:

```json
{"schema":"imagejxx.channel-display","version":2,
 "mode":"composite","projection":"max",
 "channels":[{"visible":true,"range":[0,255],"lut":{"name":"Red"}}]}
```

The representation decision must freeze all of these details together:

- Preserve V1 encode/decode and normalized V1 command bytes/semantics. Existing
  V1 Set/Reset/Disable records, absent-state defaults and explicit SUM creation
  retain their current representation. V1 interpretation is SUM. V2 SUM is
  legal if it has been explicitly created; retaining schema identity needs a
  typed encoding/version choice or a distinct V2 envelope, not a renderer that
  re-encodes every SUM asV1.
- Keep the persisted-state and executable-action schemas distinct. A V2 action
  must contain its complete validated resolved state, original source binding
  and any deliberate navigation/transition effect. V1 action parsing remains
  exact and cannot accept V2 state or extra fields. Strict replay retains the
  original validated record and never reruns LUT transformation or reset.
- Typed explicit state application and a source-derived **Select Max** intent
  are different operations if the latter transforms existing LUTs/flags or C.
  Freeze the minimal native request/action form for that intent. Resolve it
  once from the captured source state; do not put the transformation in the
  panel or renderer. Validate a captured-display dependency before original
  intent publication if it consumes mutable display state. Strict replay of a
  resolved result remains independent of the current display configuration.
- If reference-compatible transition policy changes C, encode that explicit
  effect separately from `ChannelDisplayState`, whose active C lives in
  `DisplayState.c`. Freeze replay/rebind behavior for that effect. Existing V1
  actions continue preserving current navigation. Never smuggle a C change
  through a state that has no selected-channel field.
- Ordinary Reset range, range/LUT/visibility edits and Color/Grayscale switches
  on V2 state must retain its projection/version; their existing source and
  live-range semantics remain. Decide whether selecting ordinary Composite in
  the UI explicitly chooses SUM, as in the reference, while mode-only typed
  changes may retain projection. Encode these distinct requests unambiguously.
- Preserve P06c's existing owned visibility-retention behavior for its current
  mode actions. The reference's `setMode` flag reset is an observed difference,
  not permission to change qualified Color/Gray/SUM behavior incidentally.
  Freeze Max-entry visibility policy explicitly and record any owned difference
  from R12/R13 instead of calling both policies equivalent.
- New generic known-state hooks validate exact V1 **and** exact supported V2;
  future/unknown headers remain opaque in native V3 transport. Desktop/API
  interpretation refuses unsupported present state. Existing runtimes that
  understand onlyV1 must preserve V2 opaquely and refuse viewing it, never fall
  back to SUM. V3 file framing need not change. Legacy V2/detached export keeps
  its explicit no-loss guard.
- Canonical stored Composite above8 channels remains invalid for both
  projections. Explicit requested Composite above8 normalizes to Color without
  silently truncating channels. Freeze retained projection/version behavior
  for this fallback and test it; legacy F64/S3/S4 admission does not expand.

Alternative: a separately versioned projection property/action could leave the
V1 object untouched, but creates two authorities for one rendered state and
requires coupled validation, atomic publication, remapping, persistence and
cache keys. It also risks a V1-only reader silently showing SUM while ignoring
the extra property. Choose it only with an explicit unsupported-combination
guard and a documented reason. Adding an optional field to exactV1, overloading
`mode="max"`, dropping unknown fields or deriving projection from a legacy
flat field is not a compatible option.

**Adoption002 settles the effective contract.** It supersedes the immutable
base proposal's Max-only projection/refusal alternatives with explicit Min
representation/composition and faithful qualified Max-entry transitions. A
LUT-preserving direct Set remains distinct from native SelectMax. Native
classification uses the declared state-derived policy outside the captured
context; the R14-repeat processor-cache limitation remains explicit. Standalone
SelectMin/Invert controls and full CD05/CD07/CD08/CD09 closure remain required.
