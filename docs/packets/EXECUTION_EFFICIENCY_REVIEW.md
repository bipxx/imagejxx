## Required product behavior versus optional guarantees

Curve-preserving union/intersection/subtraction/XOR, holes/islands, captured
operands, off-canvas geometry, empty results, stable versions, atomic history,
bounded failure/cancellation and commercial eligibility remain required. A
raster result or flattened polygon cannot silently satisfy a continuous-curve
requirement. Unsupported cases remain explicit gaps until delivered.

The following are **unratified profile proposals**, not original universal
product acceptance requirements: exact topology of every binary64 dyadic input,
retaining each original segment's degree/provenance, the specific 64-ULP error
formula, a new bespoke arbitrary-precision kernel, and re-solving a second exact
arrangement for every emitted path. Do not impose them on an ImageJ-compatible
profile without a concrete compatibility need. Do not remove them from already
published contracts or relabel approximate output as exact. No production
continuous-Boolean API has yet frozen these proposed guarantees.

At geometry entry compare two contract choices and choose **one product
profile**. This is not a requirement to implement two engines. Retain binary64
native operands and results. ImageJ's float-effective domain informs reference
comparisons; it does not authorize a default lossy native solver:

1. **Reference-compatible continuous profile:** preserve curve geometry and the
   pinned ImageJ operation/fill/empty semantics at a documented precision;
   evaluate an existing eligible native curve engine behind a narrow adapter.
   Quantify boundary/topology differences on adversarial fixtures. A binary32
   computation mode, if ever added, must be explicitly named and opt-in; it
   cannot close required native64 cases that it cannot represent.
2. **Stronger exact-native profile:** exact-dyadic predicates and validated
   rounded output only if justified by user-visible requirements or demonstrated
   failures that the first profile cannot handle. Give it its own versioned
   contract and complete cases; it cannot delay unrelated editor features.

Prefer a reviewed existing engine if it meets the chosen profile, licensing,
toolchain and resource/error contract. No candidate is approved by this review.
Lib2geom, Skia and CGAL have different precision, obligations and integration
costs; source research is evidence for a decision, not incorporation permission.
If an in-process dependency cannot provide bounded recoverable behavior, that
is a real adapter/backend decision. A watchdog around reference code does not
prove native operation cancellation or allocator safety.

## Geometry decision experiment with an exit

The four uncommitted source/contract artifacts are **candidate reference tools**,
not the beginning of an unbounded framework. On resume:

1. Freeze their small protocols only after C checks the independent expected
   fixtures needed by the backend decision. Preserve exact word inputs and the
   distinction between Java float-effective geometry and native binary64.
2. Use the existing pinned ImageJ runtime for a bounded representative corpus:
   crossing, disjoint/containment, holes/islands, tangent/coincident boundaries,
   self-intersection, empty, off-canvas and tiny-scale differences. Retain actual
   observed exceptions/limitations rather than deriving expectations from product.
3. Independently verify the analytic cases that distinguish candidate behavior.
   The Fraction evaluator is a witness/reference aid, not a required production
   kernel and not proof of general root/coincidence/topology coverage.
4. Screen candidates for C++17, core-only/headless installation, standalone
   operation without Python/Java, actual license closure, recoverable resource
   behavior and native64 curve requirements; shortlist at most two. Evaluate
   one thin adapter at a time in the existing cache against the same required
   corpus plus resource/refusal/cancellation checks. Freeze mandatory success
   versus explicitly permitted refusal rows beforehand. A reference-only pass
   does not substitute for candidate behavior. Do not acquire/build CGAL merely
   because it was researched; it must resolve a named remaining decision.
5. Produce **one backend decision record**: selected profile, operation/operand
   matrix, curve/output representation, comparison thresholds fixed in advance,
   pinned license/transitive obligations, resource/cancellation approach,
   implementation, integration, packaging and maintenance cost/risk and named
   unsupported residuals. Every unsupported required category keeps an explicit
   delivery assignment. Select the lowest total cost meeting the required
   rows, rather than the shortest wrapper or most ambitious arithmetic system.
   Do not invent an
   API, new dependency checkout, JDK or full compiler cache during source review.
6. Begin one user-visible vertical slice once that decision is supported. Stop
   extending reference machinery when it no longer changes the backend choice
   or an acceptance predicate. If no candidate meets a required category, write
   the exact algorithmic blocker and schedule that module explicitly.

The experiment has no prefilled pass or time estimate. Its completion artifact
is a decision backed by observations, not “more research completed.”

## Ready queue and three-agent allocation

The numbered waves are a dependency map, not a global serial queue. When the
user resumes implementation, C selects the highest-value ready missing behavior
from these tracks after checking source/evidence. Do not use an easy duplicate
settings test to avoid harder required product work.

| Ready track | Concrete next selection | Dependency |
| --- | --- | --- |
| Workflow integration | Audit/implement manual-threshold V3 typed program/Run support using the existing direct command, strict replay and target machinery | Existing qualified core; no continuous solver dependency |
| Configuration consumers | Batch C2…C12 from the per-key guide, selecting reproduced missing behavior before pure requalification | Existing settings/preferences and consumers; no solver dependency |
| Linked viewing/slicing | Inventory missing XY/XZ/YZ and C/Z/T controls/metadata, reuse axis/slicer/channel commands and asymmetric calibrated fixture | Existing Dataset/sampler contracts; no Boolean prerequisite |
| Selection/pixel operations | Missing tool/manager/paste/text workflow using current geometry and publication | Only continuous algebra consumers wait for the solver |
| Numerical processing | Missing pinned method/options through existing target/preview/admission path | Per-method algorithm/reference readiness |
| Continuous geometry | Bounded backend/profile experiment, then native adapter and one real transaction/UI path | Only this track requires the decision above |
| Release evidence | Resolve current certification/availability mechanism and real platform gaps independently | Never bypass unavailable historical proof or claim headless UI certifies OS/GPU/accessibility |

Normal allocation remains A core, B shared UI, C assertions/integration. During
the short geometry decision, A reviews candidate semantics, B maps existing UI
consumer/refusal contracts and C gathers independent decision fixtures. Once
those outputs are delivered, move A/B to a ready feature; do not occupy all three
agents on more documentation while C alone gathers references. C serializes
product build/install, not every read-only/source preparation action.

## Definition of efficient completion

For each API/key: existing seam, specific missing behavior, smallest code change,
independent oracle, impacted consumers and final acceptance are named before
work. Prefer the existing public API over a new one; prefer a shared adapter over
duplicate frontend logic. Test the actual consumer once per distinct semantic
path and preserve exhaustive numerical/validation coverage at the owning layer.

Use one current status record with separate implementation, verification and
evidence-availability states. A focused pass never closes an entire family by
itself. All99 states remain47 in progress/52open/0complete; commercially eligible
Fiji discovery, macOS, real OS/GPU/accessibility, release packaging and every
unfulfilled M0–M13 requirement remain in scope.

For the next three implementation packets, record a small efficiency ledger:
user-visible missing clauses closed, reused versus new implementations, affected
selectors rerun, rebuilds caused by actual consumed changes, producer/reader
failures, retained bytes and cleanup bytes, and integration waiting time.
Investigate a packet that changes only probes/docs without closing a previously
unproved required consumer or behavior. Counts measure effort and evidence scope,
not functionality percentages; never optimize by reducing required assertions
or choosing easy unrelated work while the main deliverable is ready.
